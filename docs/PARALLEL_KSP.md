# Parallel KSP / PC: the SNES-diverges-step-0 fix (pass-12 followup 3)

This document records the diagnosis and fix for the twelve example
configs that were listed in `tests/CMakeLists.txt` under
`EXAMPLE_SMOKE_MPI4_KNOWN_BROKEN` with the comment "SNES diverges step 0"
when the `examples_runtime` CTest gate ran them at `MPI_RANKS=4`.

The committed baseline / post-fix run logs referenced below live in
`tests/diagnostics/parallel_ksp_baseline/<N>_<event>.mpi4.log` and are
regenerated by the `Diagnostic.ParallelKSP.<N>_<event>.BaselineMPI4Capture`
CTest tests (label `diagnostic`). The capture options are documented in
`tests/diagnostics/capture_parallel_ksp_baseline.sh`.

## TL;DR

- Ten of the twelve fail for one reason: `Simulator::setupSolvers()` puts
  the elastodynamics solver on `KSPPREONLY` + `PCLU` (a direct solve),
  then `scripts/run_with_mpi.sh` overrode `-pc_type` to `bjacobi` for the
  parallel run without also overriding `-ksp_type`. `KSPPREONLY` applies
  the preconditioner exactly once per linear solve. With a direct LU PC
  that is an exact solve, so serial Newton converges quadratically. With
  a block-Jacobi PC it is a single block-Jacobi sweep, which is a
  fixed-point iteration, not a Newton step. SNES stalls and reports
  `DIVERGED_MAX_IT` at step 0, then `TSStep ... DIVERGED_NONLINEAR_SOLVE`.
- The fix is to add `-ksp_type gmres` to the parallel option string in
  `scripts/run_with_mpi.sh`. That wraps the block-Jacobi preconditioner
  in a real Krylov loop. With the change, every one of the ten converges
  in a single SNES iteration (5 to 9 GMRES iterations per linear solve on
  the canonical 8448-DOF nuclear mesh).
- The remaining two were mislabelled in the known-broken list. They are
  not KSP failures at all: `06_gmsh_multimaterial` aborts in
  `DMPlexCreateGmshFromFile` because its `mesh_file` relative path was
  not updated when pass-12 moved the config into the example directory
  (`../meshes/...` should be `../../meshes/...`), and `17_velocity_model`
  aborts in `populateAuxFieldsByVelocityModel` because the example never
  shipped the `velocity_model.bin` it references. Both are fixed
  example-side: a one-line path correction and a committed 12 KB binary
  fixture generated by `scripts/generate_velocity_model.py`.

## Diagnosis

### Baseline capture

For each example, `tests/diagnostics/capture_parallel_ksp_baseline.sh`
runs the example's `run.sh` at `MPI_RANKS=4` under a smoke budget with

```
PETSC_OPTIONS="-snes_monitor -ksp_monitor_true_residual \
  -snes_converged_reason -ksp_converged_reason -snes_linesearch_monitor \
  -snes_view -snes_max_it 12 -ksp_max_it 200 -ts_max_steps 1 -options_left"
```

The `-pc_type bjacobi -sub_pc_type lu` (baseline) or
`-ksp_type gmres -pc_type bjacobi -sub_pc_type lu` (post-fix) string is
the one `scripts/run_with_mpi.sh` injects on the command line, so it wins
over the `PETSC_OPTIONS` env entries.

### Why KSPPREONLY + bjacobi stalls

The relevant lines are `src/core/Simulator.cpp:5763-5764`:

```cpp
ierr = KSPSetType(ksp, KSPPREONLY); CHKERRQ(ierr);
ierr = PCSetType(pc, PCLU);         CHKERRQ(ierr);
```

followed by `KSPSetFromOptions` / `PCSetFromOptions`. On a serial run
nothing overrides those, so the linear solve is a direct LU and each
SNES iteration is a true Newton step. On a parallel run
`scripts/run_with_mpi.sh` appends `-pc_type bjacobi -sub_pc_type lu`
(because the PETSc 3.25 build in the FSRM image has no MUMPS or
SuperLU_DIST, so a parallel direct solve is not available). That changes
the PC but not the KSP type, so the KSP stays `preonly`.

The `-snes_view` block in the baseline log makes the failure mode
explicit:

```
KSP Object: 4 MPI processes
  type: preonly
  ...
  not checking for convergence
PC Object: 4 MPI processes
  type: bjacobi
    number of blocks = 4
    ...
total number of linear solver iterations=12   # 1 per Newton step
```

and the `-snes_monitor` / `-snes_linesearch_monitor` lines show the SNES
residual shrinking by a constant factor of roughly 0.5 per iteration
(the block-Jacobi spectral radius), full step accepted each time,
without ever reaching the convergence test inside 12 (or, in the
production run, 50) iterations.

### Why the matrix itself is healthy

The "unpreconditioned" sweep entry below converges in about 35 GMRES
iterations, so the operator (`M/dt^2 + ... + K` for the TSALPHA2
elastodynamics system, mass-dominated at `dt = 1 ms`) is well
conditioned. The bug is the missing Krylov loop, not the matrix and not
the preconditioner.

## PC sweep

Sweep on `09_gasbuggy_1967` at `MPI_RANKS=4`, smoke budget, run via
`FSRM_MPI_PETSC_OPTS=<string> MPI_RANKS=4 bash run.sh` (the env var
replaces the helper's default option string):

| Option string | Outcome | KSP iters / linear solve | SNES iters / step |
|---|---|---|---|
| `-pc_type bjacobi -sub_pc_type lu` (the broken default; KSP stays `preonly`) | `TSStep DIVERGED_NONLINEAR_SOLVE` at step 0 | 1 (one block-Jacobi sweep) | hits `DIVERGED_MAX_IT` |
| `-ksp_type gmres -pc_type bjacobi -sub_pc_type lu` (**adopted**) | completes | ~5 to 9 | 1 |
| `-ksp_type gmres -pc_type bjacobi -sub_pc_type ilu` | completes | ~5 to 9 | 1 |
| `-ksp_type gmres -pc_type asm -sub_pc_type lu` | completes | ~0 to 4 | 1 |
| `-ksp_type gmres -pc_type asm -pc_asm_overlap 2 -sub_pc_type lu` | completes | ~0 to 3 | 1 |
| `-ksp_type gmres -pc_type gamg` | completes | ~4 to 8 | 1 |
| `-ksp_type gmres -pc_type none -ksp_gmres_restart 100` (diagnostic) | completes | ~35 | 1 |

Every Krylov-wrapped choice works. Additive Schwarz with overlap heals
the inter-rank coupling and shaves a couple of iterations, and GAMG is
comparable, but on this problem size the differences are noise. The
adopted fix is the minimal delta from the existing default: keep
`-pc_type bjacobi -sub_pc_type lu`, just add `-ksp_type gmres` in front.
That preserves the pass-12-followup-2 behaviour for every example that
was already converging (the three showcase examples Salmon, Sedan, and
Punggye-ri were re-run before and after the change and are unchanged)
while restoring a real solve for the ten that were not.

## Fix

`scripts/run_with_mpi.sh` default parallel option string changes from

```
-pc_type bjacobi -sub_pc_type lu
```

to

```
-ksp_type gmres -pc_type bjacobi -sub_pc_type lu
```

Override per run with `FSRM_MPI_PETSC_OPTS` (set to empty to disable the
injection entirely). No C++ changes; the launcher already owned this
option string and the brief for this pass forbids physics changes.

All twelve are removed from `EXAMPLE_SMOKE_MPI4_KNOWN_BROKEN` in
`tests/CMakeLists.txt`; their `ExamplesRuntime.<N>.MPI4` tests flip from
`WILL_FAIL TRUE` to ordinary pass. The three cohesive-cells fault
examples (`04_locked_fault`, `08_time_dependent_slip`, `16_scec_tpv5`)
stay in the known-broken list: they are blocked on the PETSc 3.25
saddle-point solver tracked in `docs/SOLVER_STATE.md`, which is a
separate axis from this launcher fix.

## Not in scope

No physics changes, no SNES/KSP tolerance relaxation in the production
path, no changes to `src/io/ConfigValidator.cpp` or the
`examples_runtime` gate infrastructure beyond removing entries from the
known-broken list, no Schwarz coupled far-field, no monolithic source
mesh. Those are pass-14 and later.
